# 从 MIDI 制作关卡

MIDI 提供演奏事件；声部分组、GS 音色选择、混音和击拍职责仍需制作判断。流程产出项目已有的 `MultipartScore`，在制作阶段完成转换，播放器无需新增 MIDI 解析依赖。

## 解析并确定声部

优先使用成熟解析库，例如 Python `mido`，查阅其[文件读取文档](https://mido.readthedocs.io/en/stable/files/midi.html)。依赖使用项目环境或 `uv run --with mido` 的隔离环境，不为单曲转换安装全局包或修改前端依赖。

记录源文件路径与校验和；检查文件类型、时间分辨率、轨道／通道、拍号、速度及 program/bank 事件。扫描所有轨道中的元信息，控制轨不一定排在首位。

- Type 1 的轨道共享起点；Type 0 可能在单轨中包含多个通道。结合通道、音区和音乐材料确定声部，不把“轨道数”直接当作“声部数”。同一乐器允许保留多个独立声部。
- 对 Type 2 的独立序列或 SMPTE 时间制，先明确如何映射到共同拍位；下述 PPQN 换算不能直接套用。
- 核对整个速度图和拍号图。缺失元信息时记录所采用的 MIDI 默认值或外部依据，不声称是作曲者标注。变速／变拍超出当前关卡契约时，按主 skill 的限制处理。

## 还原音符与时间轴

逐轨读取时，`message.time` 是 delta ticks；先在各轨内累加为绝对 tick，再按事件的通道和音高配对起音、收音。`note_on` 的力度为 0 也表示收音。注意 `MidiFile` 的合并迭代可能给出秒数，不能将其再次当 ticks 换算。

对于 PPQN 文件，以四分音符为一拍：

```text
beat     = noteOnTick / ticksPerBeat
duration = (noteOffTick - noteOnTick) / ticksPerBeat
```

保留音高、同拍和弦、不同释放时间、休止和跨小节持续音。MIDI 音高已是实际演奏音高，不因乐器名称再次作移调。同音重叠起音不能用单个字典值覆盖；显式配对并说明歧义，未配对或非正时值事件要定位到轨道／通道／tick。

检查踏板、弯音、控制器和中途音色切换，区分 note-off 时刻与踏板后的实际发声尾音。当前数据模型未表达的效果须明确取舍或转换依据，不能静默丢弃后声称完全等同原文件。

依据拍号、起点和结束事件建立 `bars`，核对末音结束与末尾休止。开头有休止不等于弱起；尾部事件时间也不一定就是音乐长度。MIDI 通常已展开反复，不再按纸面符号重复展开。

## 生成音乐，再编排击拍

将确认后的声部写成有稳定 ID 的 `parts`，保存可回查源事件的音符数据。原始力度通常可按 `velocity / 127` 映射；若像本次巴赫文件一样全部为 127，先判断其是否只是导出默认值，再设置适合游戏的力度。力度调整、声部增益和音色替换分别记录，不把某曲的数值固定为所有 MIDI 的默认值。

在保留音乐的基础上独立编排 `hits`：根据乐句选择声部和交接位置，用音符引用表达；跨声部同拍和弦可合为一次击拍。MIDI 通常没有“玩家应敲哪个声部”的标注，交接属于关卡设计。过密装饰音可保留自动演奏并注明取舍，不必删除音符或修改节奏。单旋律或固定声部适合的曲目无需强行加入接力。

## 核对与交付

生成后将各声部音符与解析出的源事件逐项比较，检查音符数量、音高、起始拍位和持续时间；保留重复事件的数量，不能只比较集合。比较 tick 或有依据的数值容差，已批准的变换单独列明。不要仅用从同一生成文件反推的数据证明转换正确。

再运行主 skill 的谱面、路线与浏览器验收，重点覆盖本曲实际存在的声部交接、同拍和弦、跨界延音和结尾收音。自动检查确认事件、发声与资源清理，用户试听确认混音与交接听感。

关卡 README 记录来源、轨道到声部的对应、时间及效果取舍、混音调整与击拍选择。交付时区分“与 MIDI 演奏事件一致”和“已核对纸面乐谱”：指法、连奏弧及装饰符号写法不能仅凭 MIDI 还原。
